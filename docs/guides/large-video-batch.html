网页视频批量下载：几百 MB 也不失败

很多人第一次尝试网页视频批量下载，都会在总量涨到几百 MB 时遇到同一类问题：进度条停在某个位置不动、 最终报一个看不懂的错误，或者浏览器直接变得很卡。这通常不是网速的问题，而是「先把所有文件读进内存、 再组装成一个压缩包」这种做法的固有上限。这篇教程解释失败的原因，以及两个体积阈值如何让大文件自动改走逐条直下。

本文内容

  1. 失败的原因：整包先在内存里组装
  2. 两个阈值：50MB 与 500MB
  3. 视频默认不进压缩包
  4. 分卷打包与进度可见
  5. 这些情况本扩展不处理

失败的原因：整包先在内存里组装

压缩包（ZIP）是一种需要「先知道全部内容、再写中央目录」的格式，因此最直观的实现方式是把待打包的每个文件 完整读入内存，全部拿到之后再一次性生成压缩包并交给浏览器下载。批量下载几十张小图时这套流程很快， 但一旦总量到几百 MB，内存占用会随文件数线性增长：轻则打包变慢、进度长时间停在原地， 重则这个后台任务被浏览器回收，表现就是「点了下载，最终什么都没有」。

解决办法不是把内存调大，而是在体积过线时干脆不打包：让每个文件各自作为一次普通下载， 由浏览器自己流式写盘，扩展只负责调度与状态记录。

两个阈值：50MB 与 500MB

扩展在开始下载前会先算一遍这批资源的大小，然后据此选择传输方式：

  • 单文件超过 50MB：整批改为逐条直接下载。单个文件就到这个量级时，它本身已经不适合走内存打包。
  • 整批预估超过 500MB：同样改为逐条直接下载，避免「每个文件都不大、加起来却很大」的情况。
  • 两者都没超过：按卷打包成 ZIP，打包在后台的 offscreen 文档中完成，关掉弹窗不会中断。

对于无法读到文件大小、只能从页面元素上推断的视频（这类条目的体积显示为 0），扩展会按一个保守值估算， 宁可让它走直下，也不赌它很小。直下模式下的并发数会自动压低，避免同时写多个大文件把磁盘 IO 占满。

视频默认不进压缩包

v1.6 起，视频条目默认不参与打包：当你同时选中图片和视频时，扩展会把批次拆开处理——视频逐条直接下载， 图片按上面的阈值决定打包或直下，最后在结果提示里分别报数（例如「视频 3 个已逐条下载，图片已打包」）。 这样你既不用手动分批，也不会因为一个 800MB 的视频把整批图片的压缩包一起拖垮。

如果你确实希望视频也进压缩包（例如为了方便归档），可以在扩展的 Options 页里关闭 「视频逐条下载（不打包）」；关闭后视频会回到与图片相同的阈值判定逻辑。

无论哪种方式，最终都由浏览器的下载能力写入磁盘，扩展只提交下载任务并跟踪状态； 相关能力可对照 Chrome 官方 downloads API 文档。

分卷打包与进度可见

打包也不会无上限地堆积：单卷最多 200 个文件、预估不超过 500MB，超出的部分自动切到下一卷， 文件名会带上 _part2、_part3 这样的后缀。每完成一卷就立刻回写该卷条目的状态， 因此即使后续某一卷失败，前面已经下好的卷也不会白费。

进度与失败原因是全程可见的：打包时按钮上会显示「第 1/3 卷 12/200」这样的计数； 结束后如果仍有失败项，提示里会列出前几条具体原因（例如 HTTP 403），而不是只给一句「失败 N 个」。

这些情况本扩展不处理

  • m3u8 / HLS 分片流：这类视频由成百上千个分片组成，需要专门的合并流程，本扩展只接受直链视频，不做分片合并。
  • 加密内容：需要解密才能播放的资源不在支持范围内，扩展也不做任何绕过。
  • 需要登录态的直链：默认不带 Cookie 的跨域请求会被站点拒绝。可以在 Options 里开启「打包时携带 Cookie」后重试，并注意这会把该站点的 Cookie 一并带给打包请求。
  • 站点已改为按需鉴权：如果视频地址带有短时效签名，过期后再下载会失败，回到页面重新触发一次捕获即可。
